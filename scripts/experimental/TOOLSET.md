# Conjunto de compilación experimental

`get_build_utilities.ps1 -Destination <carpeta nueva>` obtiene CMake 3.31.6, Ninja 1.12.1 y Python 3.14.0 embebible de sus fuentes oficiales, comprueba los SHA-256 fijados y extrae las herramientas sin instalarlas. `-PackageCache` admite archivos descargados previamente y vuelve a verificarlos. El hash de CMake coincide con el archivo de sumas publicado por Kitware; los de Ninja y Python se fijaron a partir de las descargas observadas.

`assemble_toolset.ps1 -Destination <carpeta nueva> -ComponentsRoot <carpeta>` reúne los componentes ya extraídos. Deben estar bajo `ComponentsRoot/msvc`, `windows-sdk`, `llvm`, `utilities` y `rexglue`, respectivamente como los generan `get_msvc.ps1`, `get_windows_sdk.ps1`, `get_llvm.ps1`, `get_build_utilities.ps1` y `get_rexglue_sdk.ps1`. El script comprueba que existan antes de copiar; aún no ejecuta las descargas por sí mismo. Su salida ocupa 1.184.681.965 bytes en la prueba, sin optimizar.

`prepare_toolset.ps1 -Destination <carpeta nueva> -WorkingDirectory <otra carpeta nueva>` coordina esos pasos y coloca la salida en el destino solo después del ensamblado. `-CacheRoot` acepta subcarpetas `msvc`, `windows-sdk`, `llvm` y `utilities` con paquetes ya descargados, siempre verificados por sus hashes. En una ejecución con PowerShell 5.1 se usaron copias locales de esos paquetes y se descargó ReXGlue; la salida coincidió por SHA-256 archivo por archivo con el conjunto anterior que compiló correctamente: 14.978 archivos, sin diferencias. No se probó en esta ejecución la descarga por red de todos los paquetes ni la reanudación de una interrupción; la carpeta temporal se conserva para inspección.

Una ejecución posterior de `prepare_toolset.ps1` sin caché descargó y verificó todos los componentes, extrajo los paquetes y terminó el ensamblado con Windows PowerShell 5.1. Después, una exportación limpia del port generó y compiló el ejecutable con esa salida. Los archivos del juego ya estaban extraídos y se usaron como entrada mediante una unión. La prueba se realizó en esta PC; no comprueba independencia de todas las DLL instaladas, no incluye la DLL gráfica corregida ni verifica un partido. La carpeta temporal se conserva y la reanudación de una descarga interrumpida sigue pendiente.

Se ejecutaron la extracción de utilidades y el ensamblado con PowerShell 5.1, y desde una exportación limpia se generó y compiló el juego con el conjunto resultante. Los componentes provenían de descargas verificadas de Microsoft, LLVM, Kitware, Ninja, Python y ReXGlue, con los archivos del juego ya extraídos. El proceso usó rutas y cabeceras explícitas y un PATH reducido en esta PC; no es una auditoría completa de archivos ni una prueba en Windows limpio. No se abrió el ejecutable ni se comprobó una partida con esta build.

Sigue pendiente coordinar las descargas desde el lanzador, reducir tamaño, resolver las condiciones aplicables a los componentes Microsoft, proporcionar la DLL gráfica corregida y verificar la primera preparación y el segundo arranque sin conexión en otra máquina.

Una alternativa a investigar es compilar con una cadena abierta basada en MinGW. No basta con reemplazar el compilador en el comando actual: el port enlaza `rex::runtime` del SDK precompilado y el archivo `rexruntimerd.lib` expone símbolos C++ con nombres de Microsoft, incluidos tipos de `std::vector`. Una cadena MinGW normalmente usa otra ABI de C++ y otra biblioteca estándar. Para evaluarla hay que reconstruir ReXGlue y sus dependencias para esa ABI y comprobar también Direct3D y el complemento gráfico; esta inspección no demuestra que esa alternativa funcione.

Prueba local con llvm-mingw 20251021 (Clang 21.1.4), ReXGlue `f5337cdc947ff6d4c4196737e2c807a48f2a1fc2` y sus submódulos: CMake configuró D3D12, pero la compilación no terminó. Para avanzar experimentalmente se cambió `HAVE_LIBC_MSVCRT` a 0 en la configuración de FFmpeg, se materializaron los enlaces simbólicos de libmspack que Git para Windows había extraído como texto, se habilitó la alternativa existente de `clock_cast` para libc++, se agregó `-mssse3` y se omitió la excepción de nombre de hilo para depuradores antiguos. Después la compilación se detuvo porque MinGW no incluye `DXProgrammableCapture.h`. Estos cambios solo existen en una copia aislada y no están validados funcionalmente; faltan resolver esa cabecera, completar la compilación y probar el juego. Los [DirectX Headers oficiales](https://github.com/microsoft/DirectX-Headers) tienen licencia MIT, pero no se ha verificado que resuelvan esa cabecera concreta.

La continuación desactivó la detección de captura gráfica en MinGW, declaró los identificadores COM de DXC y adaptó llamadas de Windows y la detección de endian. Con esos cambios, la compilación completa de ReXGlue terminó, incluyendo `rexglue.exe`, `librexruntime.dll` y `librexgpu-xenos.dll`; `rexglue.exe --help` arrancó correctamente con las DLL de llvm-mingw en PATH. El parche experimental de ReXGlue está en `patches/experimental-rexglue-mingw.patch`; además requiere el ajuste de FFmpeg, resolver los enlaces de libmspack y configurar `-DCMAKE_CXX_FLAGS=-mssse3`. No contiene los parches de sombras, no se probó generar ni compilar el juego y no se comprobó la DLL gráfica en ejecución. La detección de captura permanece desactivada en esta prueba.

En una prueba posterior, `rexglue.exe codegen` con la copia compatible del XEX generó 237 archivos en una exportación aislada del proyecto. CMake configuró el port con el SDK MinGW y compiló sus archivos, pero el enlace del ejecutable falló con símbolos como `__imp__RtlEnterCriticalSection`: ese prefijo coincide con el mecanismo de importación de DLL de MinGW y la biblioteca generada no ofrece las referencias que espera el enlazador. También se observó que Clang para MinGW ignora `-fasync-exceptions`, por lo que aun resolviendo el enlace será necesario comprobar el manejo de excepciones en ejecución. El ejecutable no se obtuvo ni se inició; las sombras y una partida siguen sin verificar.

Se evitó esa colisión reemplazando el prefijo en las fuentes del SDK, las fuentes del port y el código generado, y se enlazó con `-municode`. `rename_mingw_imports.py` reproduce el reemplazo en copias aisladas; hay que ejecutarlo antes de reconstruir el SDK y el juego. Tras copiar la DLL gráfica al nombre que espera el cargador, el ejecutable arrancó, inicializó Direct3D 12 y comenzó a ejecutar el juego, pero terminó después de unos tres segundos con `0xC0000005` (violación de acceso). El log quedó en `rwc2011-mingw-game/testdata/game.log` en la máquina de prueba. Se usaron datos y guardados aislados; las sombras corregidas no estaban integradas. La causa de la caída no se ha determinado y la advertencia de excepciones continúa pendiente.

Una traza posterior situó la caída en `__intrinsic_setjmp`, al almacenar un registro con una instrucción que requiere alineación de 16 bytes; la llamada procedía de `ppc_setjmp` y el compilador advertía que el búfer podía tener solo 8 bytes de alineación. Se cambió el código generado para guardar cada `jmp_buf` en una estructura `alignas(16)` y se recompiló el juego. En una prueba aislada, el proceso permaneció activo 20 segundos y cargó recursos; se cerró manualmente al terminar la observación. El parche `patches/experimental-mingw-jmp-alignment.patch` aplica el mismo cambio a la plantilla del generador, pero todavía falta probar una regeneración completa con ese parche. Esto no verifica una partida, guardados, sombras ni el manejo posterior de `longjmp`.
